## 视觉系统总体方案

### 功能描述

让小车通过摄像头识别场地道具（能量单元 / 能量核心），解算目标坐标（PnP），并把结果通过 ROS2 话题发送给决策与控制环节，为正式比赛中的半自动/自动收集提供感知数据。

| 指标 | 目标 | 当前状态 |
| --- | --- | --- |
| 识别对象 | 能量单元（白，30×30×30mm）/ 能量核心（黄） | ✅ 模型已训练并可推理（软件层） |
| 坐标输出 | 目标相对坐标（PnP 解算） | 🟡 软件流程已跑通，待硬件联调【待实测】 |
| 实时性 | FPS、延迟、识别率满足运动控制需求 | ⬜ 未测试【待实测】 |
| 硬件载体 | 摄像头 + 车载平台部署 | 🟡 硬件已部署并完成单链路验证，整车端到端联调进行中【待实测】 |

### 开发历程

**双环境架构的由来（选型对比）。** 最初所有环节都规划在虚拟机内完成，但很快遇到性能瓶颈：虚拟机虽然可以虚拟化 CPU、内存、磁盘和网卡，但默认难以直接调用宿主机独显的 CUDA 加速，YOLO 推理帧率极低——分辨率稍高即严重掉帧、画面卡顿，只能靠代码强制降低分辨率维持流畅度；而训练数据是手机拍摄的高清照片（120+ 张，含约 800 个目标实例），推理分辨率过低又会导致识别效果极差、置信度过低。最终把架构拆分为双环境分工：

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 纯虚拟机 | Ubuntu + ROS2 + OpenCV + YOLO 全部跑在虚拟机 | 环境隔离、安装便捷、快照可回滚、不污染宿主机磁盘 | 无法使用独显 CUDA，YOLO 推理性能差，高清视频流掉帧严重 | 不可行 |
| 纯宿主机 | 全部跑在 Windows 宿主机 | 可用 CUDA，性能充足 | ROS2 生态在 Windows 上支持差、依赖安装繁琐 | 不可行 |
| **双环境分工（选用）** | 虚拟机跑 ROS2 节点与 PnP 解算；宿主机读取视频流并跑 YOLO 推理，检测结果以 ROS2 话题回传虚拟机 | 各取所长：ROS2 生态 + CUDA 性能；两侧环境互不干扰 | 需要处理跨机通信（已由 NAT 改为桥接，见《硬件部署》章节） | ✅ 软件流程已跑通 |

**双机通信方案的演进。** 通信最初采用 NAT 网络 + 虚拟机内写定宿主机 IP 的临时方案，实测发现该方案无法支撑接入车载外部设备（ESP32）的需求——NAT 下外部设备无法主动访问虚拟机内部地址，且每次热点重启 IP 漂移导致链路极不稳定。现已彻底改为**桥接模式**，虚拟机作为局域网内的独立节点直接获取 IP，并固定宿主机、虚拟机、开发板三方静态 IP，彻底消除网络穿透问题。详见《硬件部署：网络架构（NAT → 桥接）》。

## ROS2 节点与代码结构

### 功能描述

视觉软件分为虚拟机侧与宿主机侧两部分：

- 虚拟机侧（ROS2 工作空间）：
  - `aim_interfaces`：自定义消息包，定义检测结果消息 `AimInfo.msg`；
  - `armor_detector`：检测节点包，含节点实现、参数配置与启动文件；
  - `vm_receiver.py`：ROS2 侧接收脚本，接收宿主机发来的检测结果。
- 宿主机侧（图像推理）：
  - `host_infer.py`：读取视频画面并运行 YOLO 推理；
  - `best.pt`：自训练模型权重。
- 车载端（新增，见《硬件部署》章节）：
  - 板1 图传固件：OV2640 采集 + UDP 推流；
  - 板2 MicroROS 客户端：订阅 PnP 结果话题 + 串口转发 STM32。

## 虚拟机环境搭建（Ubuntu 22.04 + ROS2 + OpenCV）

### 功能描述

提供 ROS2 运行与开发环境：支持节点编译（colcon）、OpenCV（Python 与 C++ 双接口）、视频编解码与摄像头读取依赖。该环境已可编译运行。

### 开发历程

**1）安装 VMware17 与 Ubuntu 22.04**

- VMware17 安装教程：<https://zhuanlan.zhihu.com/p/1951919938420865019>
- Ubuntu 22.04 安装教程：<https://blog.csdn.net/C_1Y1_T/article/details/130243874>

**2）基础环境（ROS2 等）。** 使用 fishros 一键安装工具：

```bash
wget https://fishros.com/install -O fishros && . fishros   # 以 fishros 官网首页命令为准
```

按提示输入密码后进入菜单，依次输入：`5`（更换系统源）→ `7`（VS Code）→ `1`（一键安装 ROS，**注意选对 ROS2 版本**）→ `0` 退出。

随后：

```bash
sudo apt install g++        # 安装 g++
sudo apt install cmake      # 安装 cmake
python3 -m pip install --user numpy   # Python 基础依赖
```

**3）OpenCV 安装。**

- Python 版：`sudo apt-get install python3-opencv`
- C++ 版（源码编译）：

```bash
# 1. 安装依赖项
sudo apt update && sudo apt install -y cmake g++ wget unzip
# 2. 创建 opencv_build 文件夹并进入
mkdir opencv_build && cd opencv_build
# 3. 下载 opencv 及 opencv_contrib 源码压缩包并解压（网络问题可自行下载后解压）
wget -O opencv.zip https://github.com/opencv/opencv/archive/4.x.zip
wget -O opencv_contrib.zip https://github.com/opencv/opencv_contrib/archive/4.x.zip
unzip opencv.zip && unzip opencv_contrib.zip
# 4. 创建构建目录并切换
mkdir -p build && cd build
# 5. 配置并编译
cmake -DOPENCV_EXTRA_MODULES_PATH=../opencv_contrib-4.x/modules ../opencv-4.x \
      -DBUILD_opencv_highgui=ON -DBUILD_opencv_imgcodecs=ON \
      -DBUILD_opencv_videoio=ON -DBUILD_opencv_objdetect=ON
cmake --build . -j$(nproc)
# 6. 安装
sudo cmake --install .
```

**4）视频与图像依赖（含摄像头读取）。**

```bash
# 视频编解码
sudo apt install libavcodec-dev libavformat-dev libswscale-dev
sudo apt install libgstreamer-plugins-base1.0-dev libgstreamer1.0-dev
# 图像与 GUI
sudo apt install libgtk2.0-dev libgtk-3-dev libjpeg-dev libpng-dev libtiff-dev
# v4l2（读取硬件摄像头用）
sudo apt install v4l-utils libv4l-dev
# 刷新动态链接库
sudo ldconfig
```

**5）MicroROS 相关依赖（车载端接入，2026-10-19 补入）。** 板2 通过 MicroROS Agent 与虚拟机通信，虚拟机侧需提供 MicroROS Agent：

```bash
# MicroROS Agent（Ubuntu 22.04 / ROS2 Humble）
# 具体安装方式以 micro-ros-agent 官方仓库为准
git clone -b humble https://github.com/micro-ros/micro_ros_agent.git
cd micro_ros_agent && mkdir build && cd build
colcon build
source install/local_setup.bash
ros2 run micro_ros_agent micro_ros_agent udp4 --port 8888
```

**踩坑与要点：**

| # | 坑/要点 | 处理 |
| --- | --- | --- |
| 1 | fishros 菜单里 ROS 版本众多，装错版本后 colcon 编译报错 | 安装时确认选择 ROS2 对应版本 |
| 2 | OpenCV 源码包下载可能超时 | 换网络或到别处下载压缩包后再解压编译 |
| 3 | 摄像头读取依赖缺失时 `VideoCapture` 打不开设备 | 提前安装 v4l2 系列依赖 |
| 4 | 虚拟机 NAT 模式下外部 ESP32 无法访问虚拟机内部地址 | 改为桥接模式，见《硬件部署》章节【待实测：桥接稳定性】 |

## 数据集制作与模型训练

### 功能描述

用自建数据集训练面向比赛道具的检测模型：数据来源为在交创中心拍摄的 120+ 张高清照片（含约 800 个目标实例）；训练产出 `best.pt` 权重供推理使用。

### 开发历程

**1）标注流程。** 在终端打开标注工具根目录：

```bash
python main.py
```

在工具中打开装好图片的文件夹，新建类别后框选目标，处理完全部图片后保存，会在图片目录生成 `data.yaml` 与 `labels/` 文件夹。

**2）数据集结构：**

```text
D:/Yolo/dataset_images/     # 数据集根目录（示例路径）
├── data.yaml
├── images/
│   ├── train/              # 训练集图片（建议约八成）
│   └── val/                # 验证集图片（建议约一成）
└── labels/                 # 标注文件（与 images 顺序严格对应）
    ├── train/
    └── val/
```

剩余约一成图片建议留作推理验证；总图片数量不能太少。注意检查 `data.yaml` 的类别索引定义（哪个类别是 0、哪个是 1），索引错误会导致训练结果完全不可用。

**3）训练命令：**

```bash
yolo task=detect mode=train model=yolov8n.pt data=D:/Yolo/dataset_images/data.yaml epochs=50 imgsz=640 batch=8 workers=0
```

参数说明：

| 参数 | 含义 | 取值理由 |
| --- | --- | --- |
| `model=yolov8n.pt` | 预训练权重（n 为 nano 级） | 训练快、模型小，先用小模型打通流程 |
| `data` | data.yaml 所在路径 | 必须指向实际路径 |
| `epochs=50` | 训练轮数 | 不宜过大，防止过拟合 |
| `batch=8` | 批次大小 | 与显存容量匹配 |
| `imgsz=640` | 输入图像尺寸 | YOLO 会将图片统一缩放至此尺寸 |
| `workers=0` | 数据加载进程数 | Windows 系统下取 0 最稳妥 |

训练输出保存在当前目录的 `runs/` 文件夹内。

## 推理验证

### 功能描述

用训练好的 `best.pt` 对测试图片或文件夹进行推理，输出带检测框的结果，用于验证模型效果。

### 开发历程

```bash
yolo task=detect mode=predict model=best.pt source=test.jpg conf=0.25
```

参数说明：`model` 可写绝对路径或相对路径（取决于当前终端目录）；`source` 可填写文件夹地址以批量验证；`conf` 为置信度阈值，低于此值不画框，可按现场效果灵活调整。

## 硬件部署：双 ESP32-S3 载板分工（🟡 已完成部署）

### 功能描述

视觉系统硬件采用**双 ESP32-S3 载板 + OV2640 摄像头**方案，将"图像上行"与"解算下行"两条链路物理隔离，避免单板同时承担 WiFi 推流与协议转换带来的带宽与时延竞争：

| 载板 | 型号 | 职责 | 对外接口 |
| --- | --- | --- | --- |
| **板1（前端）** | ESP32-S3-DevKitC-N16R8 | OV2640 图像采集、JPEG 压缩、UDP 图传发送 | OV2640 摄像头模组 |
| **板2（后端）** | ESP32-S3-DevKitC-N16R8 | 订阅虚拟机 PnP 解算结果、有效性校验、串口下发 STM32 | UART → STM32 |
| **主控** | STM32F103C8T6（比赛官方物资） | 接收坐标、执行运动控制与底盘动作 | 串口接收视觉坐标 |

该拓扑已实现两条链路的硬件贯通：

```text
上行（图像）：OV2640 → 板1 → UDP(MJPEG) → 宿主机 YOLO 推理 → ROS2 话题 → 虚拟机 PnP 解算
下行（坐标）：虚拟机 → ROS2 话题 → MicroROS Agent(UDP 8888) → 板2 → 串口(UART) → STM32
```

车载供电：车载电池经降压模块给两块 ESP32-S3 供电；OV2640 摄像头安装于车体前部支架【待实测：安装高度与视角标定】。

### 开发历程

#### 硬件选型对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 单板承担全部（图传 + 收结果下发） | 一块 ESP32-S3 同时做图传与串口下发 | 成本低、接线简单 | 上下行 WiFi 争抢带宽，时延抖动大，调试困难 | 不可行 |
| USB 摄像头直连宿主机 | 摄像头直接插宿主机 USB | 图像质量好、无需压缩 | 无法独立于宿主机部署，体积大，不符合作战形态 | 不可行 |
| **双 ESP32-S3 分工（选用）** | 板1 图传、板2 收结果下发 | 上下行互不干扰；两板可分置车体不同位置；便于分模块调试 | 需两套固件、多一份硬件成本 | ✅ 已部署 |

**为什么选 ESP32-S3-DevKitC-N16R8。** 该板卡内置 PSRAM（N8R8 后缀的 8MB PSRAM），是 OV2640 图像帧缓冲的必要条件；S3 系列自带 WiFi，无需外挂无线模块；N16R8 组合在 PSRAM 容量与 Flash 容量上对图像处理有余量。

#### 板1：图传链路（OV2640 → UDP → 宿主机）

**固件方案。** 基于 Arduino + `esp32-camera` 官方组件二次开发：使用官方 `CameraWebServer` 示例的摄像头初始化代码，替换其原本的 HTTP/TCP 推流逻辑为自定义 UDP 发送。

**为什么用 MJPEG/JPEG over UDP 而不是裸流。** 图像格式直接决定 WiFi 带宽占用：

| 格式 | 单帧体积（VGA 量级） | 链路特点 | 结论 |
| --- | --- | --- | --- |
| RGB565 / YUV 裸流 | ~150KB/帧 | 单帧远超 MTU，必须分片重组，丢一片即整帧报废，带宽压力大 | 不可行 |
| **JPEG / MJPEG（选用）** | 压缩后约 10–30KB/帧 | OV2640 硬件 JPEG 编码，帧自带边界，单包或少量分片即可，容错好 | ✅ 已选用 |

**UDP 分包与帧边界处理。** MJPEG over UDP 的核心难点在于"JPEG 帧边界"与"UDP 包边界"不天然对齐，需显式协议：

- 帧边界识别：JPEG 流的 SOI（`0xFF 0xD8`）与 EOI（`0xFF 0xD9`）标记作为帧起止依据；
- 分包：单帧超出 MTU 时按固定长度切分，并在包头携带帧序号与分片序号/总数，接收端据此重组并丢弃残帧；
- 丢包处理：重组失败或校验不通过的帧直接丢弃，等待下一帧，避免半帧进入 YOLO 推理【待实测：实际丢包率】。

**关键参数**（固件配置项）：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 摄像头型号 | OV2640 | DVP 接口【待回填：引脚定义】 |
| 分辨率 | `FRAMESIZE_HD`（1280×720） | HD 分辨率保证远距离小目标的可辨识度 |
| 实测帧率 | 15 FPS | 1280×720 下的稳定实测帧率【待实测：不同光照条件下的帧率与丢包率】 |
| JPEG 画质因子 | 【待回填】 | 数值越大画质越好、带宽越大；直接决定 15 FPS 能否维持 |
| 推流格式 | JPEG / MJPEG over UDP | OV2640 硬件压缩，帧自带边界 |
| 推流协议 | UDP | 无连接、开销低、延迟小 |
| UDP 目标地址 | 10.168.121.64:8888 | 宿主机 `host_infer.py` 监听端口 |
| 板1 静态 IP | 10.168.121.100 | 局域网固定地址 |

#### 板2：解算下行链路（虚拟机 → 板2 → STM32）

**下行链路总览：** 虚拟机 PnP 解算结果 → ROS2 话题 → MicroROS Agent(UDP 8888) → 板2 ESP32-S3（10.168.121.101）订阅并校验 → 串口(UART 115200) 发送 10 字节定长二进制帧 → STM32F103C8T6 解析执行。

**通信方案：MicroROS。** 板2 通过 MicroROS Agent（UDP 8888）与虚拟机通信，订阅虚拟机发布的 PnP 解算结果话题。相比"虚拟机自写 UDP 协议推包、板2 用裸 socket 解析"，MicroROS 的优势在于消息定义与 ROS2 侧天然一致，板2 无需自行维护协议解析与版本兼容性。

**MicroROS Agent 启动（虚拟机侧）：**

```bash
ros2 run micro_ros_agent micro_ros_agent udp4 --port 8888
```

板2 端订阅虚拟机的 PnP 坐标话题，收到后做**有效性校验**（如置信度阈值、目标是否丢失），再串口下发 STM32。

**为什么板2 不直接用串口连虚拟机。** 虚拟机与开发板物理分离（虚拟机在笔记本电脑内、板2 在车上），必须走无线链路；选择 MicroROS 而非自研 UDP 协议，是为了复用 ROS2 消息类型，降低两端协议不一致的风险。

#### 板2 → STM32：串口协议

板2 与 STM32 之间采用**自定义10 字节定长二进制协议**，配合 STM32 侧「DMA 接收 + 空闲中断 + 状态机」解析。

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 主控型号 | STM32F103C8T6 | 比赛官方物资 |
| 串口类型 | UART | 【待回填：具体引脚】 |
| 波特率 | 115200 | 两侧需保持一致 |
| 帧长度 | 10 字节（定长） | 定长设计便于 DMA 按帧对齐解析 |
| 数据格式 | 自定义二进制帧 | 见下方帧格式定义 |
| 坐标单位 | mm | 目标相对坐标 |
| 角度单位 | 0.1° | 偏航角，实际角度 = 角度值 / 10 |
| 校验方式 | 前8 字节累加和 | 低 8 位溢出丢弃 |
| 接收方式 | DMA + 空闲中断（IDLE）+ 状态机解析 | 不阻塞，保证高频数据下的实时性与容错率 |

**帧格式定义（10 字节定长）：**

| 字节序号 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | 帧头 1 | `uint8` | 固定 `0xAA` |
| 1 | 帧头 2 | `uint8` | 固定 `0xBB` |
| 2 | X_H | `uint8` | X 坐标高字节 |
| 3 | X_L | `uint8` | X 坐标低字节 |
| 4 | Y_H | `uint8` | Y 坐标高字节 |
| 5 | Y_L | `uint8` | Y 坐标低字节 |
| 6 | Angle_H | `uint8` | 偏航角高字节 |
| 7 | Angle_L | `uint8` | 偏航角低字节 |
| 8 | Checksum | `uint8` | 字节 0~7 累加和，取低 8 位 |
| 9 | 帧尾 | `uint8` | 固定 `0xCC` |

**X / Y / Angle 均为 `int16` 大端序（Big-Endian）**：

```text
int16 实际值 = (高字节 << 8) | 低字节   // 无符号原码拼接，按补码解释
```

即：`X = (X_H << 8) | X_L`，若结果 ≥ 0x8000 则减去 0x10000 得负值。Y、Angle 同理。

```text
完整帧结构（共 10 字节）：
┌─────┬─────┬────┬────┬────┬────┬────┬────┬──────────┬─────┐
│0xAA │0xBB │X_H │X_L │ Y_H│ Y_L│A_H │A_L │ Checksum │0xCC │
└─────┴─────┴────┴────┴────┴────┴────┴────┴──────────┴─────┘
 帧头1帧头2  ←── X (int16 BE) ──→←── Y (int16 BE) ──→←A(int16 BE)→ 校验   帧尾

Checksum = (0xAA + 0xBB + X_H + X_L + Y_H + Y_L + Angle_H + Angle_L) & 0xFF
```

**接收端解析：DMA + 空闲中断 + 状态机。** STM32F103C8T6 采用「串口空闲中断（IDLE Interrupt）+ DMA 循环接收」+ 状态机解析，避免阻塞式接收在高频数据下占用 CPU、影响其他实时任务（电机控制等）：

- **DMA 接收**：配置串口 DMA 循环模式（`HAL_UART_Receive_DMA`），数据持续流入 RAM缓冲区，不占用 CPU；
- **空闲中断触发**：一帧数据发送完毕后 UART 产生 IDLE 中断，在中断中统计本次 DMA 已收字节数；
- **状态机解析**：在中断或主循环中按帧头 → 载荷 → 校验 → 帧尾逐字节推进状态，校验通过才更新目标坐标，校验失败则丢弃并回到帧头同步状态。

典型状态机流转：

```text
WAIT_HEADER  --检测到 0xAA-->  CHECK_HEADER2
CHECK_HEADER2 --检测到 0xBB-->  RECEIVE_PAYLOAD
CHECK_HEADER2   --非 0xBB-->    WAIT_HEADER  （重同步，保留当前字节继续匹配）
RECEIVE_PAYLOAD --收满 8 字节--> CHECK_SUM
CHECK_SUM      --累加和匹配-->   WAIT_TAIL
CHECK_SUM        --不匹配-->     WAIT_HEADER  （丢弃该帧）
WAIT_TAIL      --检测到 0xCC-->   COMMIT  →  WAIT_HEADER
```

> 该设计的容错要点：采用双字节帧头 + 累加和校验，在丢包或错位场景下能快速重同步到下一个帧头，不会因单字节误码导致持续解析错乱。

**为什么用定长二进制而非 ASCII。** 定长二进制帧可由 DMA 按固定偏移直接取址解析，无需扫描分隔符，解析耗时恒定；ASCII 文本需逐字节匹配换行符，在高频数据下解析开销大且存在半包/粘包风险。累加和校验虽强度低于 CRC，但对 10 字节短帧的误码检出已足够，且计算开销极小，适合 STM32F103 这一级 MCU。

#### 网络架构：从 NAT 改为桥接

这是硬件部署过程中最关键的一次方案返工，直接决定了车载设备能否接入软件链路。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **NAT + 虚拟机内写定宿主机 IP（原方案）** | VMware 网卡 NAT 模式，在虚拟机内静态写定宿主机 IP | 配置简单 | 外部设备（ESP32）无法主动访问 NAT 内部地址；热点重启后宿主机 IP 变化需重配；链路极不稳定 | 不可行 |
| **桥接模式（选用）** | VMware 网卡改为桥接，虚拟机作为局域网内独立节点获取 IP，并固定三方静态 IP | ESP32 与虚拟机可双向直连；IP 固定、链路稳定；彻底消除网络穿透问题 | 虚拟机需与宿主机处于同一网段，网络环境变更时需重新核查 | ✅ 已完成改造 |

**桥接模式要点。** 虚拟机通过桥接网卡在局域网中成为独立节点（如 10.168.121.x 网段），ESP32 开发板与虚拟机处于同一局域网，双方可直接以 IP 寻址通信：

| 节点 | 角色 | 静态 IP |
| --- | --- | --- |
| 宿主机 | YOLO 推理端 | 10.168.121.64 |
| 虚拟机 | ROS2 + PnP 解算 + MicroROS Agent | 10.168.121.35 |
| 板1 ESP32-S3 | 图传发送端 | 10.168.121.100 |
| 板2 ESP32-S3 | MicroROS 订阅端 | 10.168.121.101 |

**端口分配。** 板1 的图传接收端口与 MicroROS Agent 端口同为 8888，二者运行在不同设备/进程中，互不冲突：

| 端口 | 协议 | 运行位置 | 用途 |
| --- | --- | --- | --- |
| 8888 | UDP | 宿主机 `host_infer.py` | 接收板1 推送的 MJPEG 视频流 |
| 8888 | UDP | 虚拟机 MicroROS Agent | 板2 以micro-ROS 客户端身份接入 |

**通信协议一致性检查清单。** 部署时需逐项确认，任一处不一致都会导致链路不通：

- [ ] 板1 固件中的目标 IP 与宿主机静态 IP 一致；
- [ ] 板2 固件中的 Agent IP 与虚拟机静态 IP 一致；
- [ ] `host_infer.py` 监听的 UDP 端口与板1 推送端口一致；
- [ ] MicroROS Agent 监听端口与板2 配置一致；
- [ ] 四方（宿主机/虚拟机/板1/板2）处于同一网段，且均不依赖 DHCP 动态分配。

**踩坑与要点：**

| # | 坑/要点 | 处理 |
| --- | --- | --- |
| 1 | NAT 模式下 ESP32 无法主动访问虚拟机内部地址 | VMware 网卡改为桥接模式 |
| 2 | 手机热点/路由器重启后 IP 漂移，链路中断 | 固定三方静态 IP，避免依赖 DHCP 分配 |
| 3 | MJPEG 单帧超出 UDP MTU 导致丢包 | 帧头携带帧序号与分片信息，接收端重组、失败即丢帧 |
| 4 | OV2640 帧缓存需 PSRAM | 选用 N16R8（8MB PSRAM）板卡 |
| 5 | 虚拟机与板2 通信端口需一致 | MicroROS Agent 统一使用 UDP 8888 |
| 6 | 1280×720 单帧体积较大，弱信号下易丢包 | 稳定帧率仅 15 FPS，需在画质因子与带宽之间权衡【待实测：实际丢包率】 |
| 7 | 串口二进制帧存在半包/粘包与错位风险 | STM32 侧采用 DMA + 空闲中断 + 状态机解析，校验失败即回到帧头重同步 |

#### WiFi 组网方案

| 阶段 | 方案 | 说明 |
| --- | --- | --- |
| 调试阶段（当前） | 手机热点 | 固定 IP 段（10.168.121.x），便于调试与复现 |
